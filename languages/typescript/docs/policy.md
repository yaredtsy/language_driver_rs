# TypeScript and JavaScript: the policy table

What the analyzer draws, and what it does not, for each feature of the language. **Every row names a fixture** and the entries built from it, and has a
snapshot of what they give: the tree and every edge, in `crates/typescript-analysis/tests/snapshots/policy/<row>.txt`. Changing a row is a policy change:
the fixture and its snapshot change in the same pull request, and the version takes a minor step (`docs/01-monorepo/06-versions-and-vnoc.md`).

The test is `crates/typescript-analysis/tests/policy.rs`. It reads this file, so **a row without a fixture, a fixture that is not there, a row without a
snapshot and a snapshot of no row each fail**, and every row's snapshot is compared with what the analyzer gives now. The last cell of a row is read by
the test: the project's folder under `tests/`, a file of it, and the qualnames to build, each in backticks (a row with the folder alone names the outline's
fixtures, a rule of the outline and not of the calls). Write the expected text by hand before running; bless it (`ANALYZER_BLESS=1`) only to write
a snapshot you then review.

A snapshot is, for each entry: the tree (the defs of the project only), then every edge of the graph as `from | callee text | what it is`, grouped by the def
the edge leaves and in source order inside it, then the counters of what no edge covers when any is above 0. `external`, `unresolved` and the counters are in
the edges, not in the tree.

This table was the contract of `typescript-v0.2.0` and becomes `typescript-v0.3.0`'s. A row whose meaning changed since v0.2.0 says so, and the
v0.3.0 tag notes list them (`docs/03-typescript/07-ts5-driver-needs.md`, row 9). The plan's version is `docs/03-typescript/06-ts4-calls.md` §5; the engine's side of each row (what
the checker answers, and where it differs) is in `ENGINE.md`.

## Reasons and counters that have no row of their own

Every `Unresolved` reason (`function_typed_value`, `any_or_untyped`, `union_receiver`, `computed_name`, `no_declaration`, `decorator_result`, `anonymous_function_called`) and every `uncovered_*` counter is named in a row above. Five more names exist in `Stats.language` and have no fixture, because no fixture can make them fire:

- `decl_not_in_outline`: a declaration the engine found in project code that the outline does not list: a bug in one of the two def rules, or a kind of declaration no rule has looked at yet. **Since D43 it never panics** (the `debug_assert!` is gone: a user's text must not stop a debug build). Every graph test goes through `tests/common`'s helper, which fails a test on this count, and the sweep (`tests/sweep.rs`) fails a real project on it. No fixture reaches it now. H13 was this count (a method signature in a type literal), found on a real file before the rule.
- `engine_kind_unhandled`: a view of the engine's node (`sem/view/`, H14) met a kind it does not handle at a place that expected one, where the code once called an engine accessor that panics. Counted with each body, failed on by `tests/common`'s helper and by the sweep. The views are proven total by a walk of every node of the bundled libraries and of the fixtures (`sem/view/tests.rs`), so no fixture reaches it; on the four projects of the sweep it is 0.
- `def_without_node`: a def whose node is missing from the program's tree, one `Unresolved` edge at the def's first byte. Tested by a test hook that drops a def's node (`calls.rs`, unit test); nothing a source file can say makes it.
- `def_written_not_called` and `def_named_not_called`: a def that is handed over and that no edge reaches. Both are 0 by construction since D22 (every hand-over has an edge); they are kept as a cross-check between the edge builder and the counter (`ENGINE.md`, "Defs handed over and not called").
