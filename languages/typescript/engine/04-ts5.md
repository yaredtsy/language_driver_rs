# TS5: driver needs, hardening H1–H10, following the disk

Part of `languages/typescript/ENGINE.md` (split out on 2026-11-24, text unchanged). Sections in the order they were written.

## TS5 step 0: what the code already had, and two answers

Checked at `e46646d` (2026-11-12) against the first version of `docs/03-typescript/07-ts5-driver-needs.md`, which was rewritten from it (its §0 lists what is built: `Cancel` with a deadline, the cancel checks before each body and each site, a cut summary walked again, `Solver::summary`, two depth/node limits that are not a frontier, `Root::Construct` everywhere but the flat solver).

**A second request on an open project is warm without the solver's memo.** V-NOC frontend, dev profile (optimized), one process, a throwaway test outside the repo: open 151 ms; then `call_graph` (a fresh `Solver` each time) on `TaskDetailPanel` 39.9 ms, 1.2 ms, 1.0 ms (90 contexts each time); `CoverageSummary` 1.3 ms then 0.03 ms; `ConfirmDialog` 4.4 ms then 0.09 ms. The warmth is `Sem`'s (`bodies`, `file_defs`) and the one checker's type caches. So TS5 keeps no solver memo between requests, and a `Session` owns only the `Project` (a memo would borrow from the struct that owns it).

**The engine is not told to stop.** The checker reads its `Context` (`tsrs_core/src/context.rs`, a Go-style context) only inside `check_source_file` (`tsrs_checker/src/checker_02.rs`), the whole-file diagnostic check, which the analyzer never calls; symbol and type queries do not read it. After a cancel it sets `was_canceled`, and `check_not_canceled` (`utilities.rs`) asserts on the next file check, so with one checker per program a link from our `Cancel` could only break the next request. `Cancel` stays at body and site granularity.

**Not answered:** `tsrs_project` depends on `tsrs_lsproto` (its `Cargo.toml`); whether its `Session` runs without a client connection is TS5 step 7's `[check]`.

## TS5 step 3: a class is a construction

A class taken as the entry of a request (`call_graph` on a def whose kind is `Class`) is `Start::Construct { class, init }`, not a walk of the class def's body. `init` and every counter come from `walk::construction`, the function a `new C()` site, a JSX element and `super()` also use, so the entry's tree is the subtree a `new C()` draws and its `Stats.language` is that construction's (tests `class_entry_*`, fixture `tests/fixtures/class-entry`; policy rows `class-entry` and `counter-class-definition`). A function or method entry is `Start::Call`, as before.

**What a class entry stopped drawing, and where it is counted now.** The class def's body (`Collector::body_of`) holds the decorators of the class, its members and their parameters, the `extends` expression, every property initializer and the static blocks. None of it is in a tree any more; `walk::construction` counts it, for the constructed class only:

- instance field initializers: `uncovered_construct_initializer_sites` (as before, over the whole chain of classes the construction goes through);
- decorators, the `extends` expression, static field initializers, static blocks: the new `uncovered_class_definition_sites`, for a class at the top of a file (`Sem::definition_sites`: the body's sites less the instance-initializer ones). Not the base chain: a base class's definition ran when it was defined;
- computed member names: `uncovered_computed_member_name_sites`, moved here from `handed_over`, so it is counted at each construction of a top-level class (it was counted only where the class def was walked, which was only an entry).

**M step 4 retired both counters**: the body that declares the class draws these sites, and a construction counts only the instance field initializers (see "Definition code in the declaring body").

`uncovered_class` is another thing: a class named where a value is handed over (`Error.captureStackTrace(this, C)`, postcss's one hit).

**Measured with a throwaway probe** (the class's body sites less its instance-initializer sites, over every class of the project, 2026-11-13): V-NOC frontend 0 of 5 classes have a definition-time site, postcss `lib/` (JS only) 0 of 19, postcss with `.d.ts` 0 of 2. The probe was checked on fixtures first (`Decorated` 11, `StaticOnly` 2, `Mixed` 1, `TopDecorated` 1, 9 classes with sites in `fixtures/uncovered`), so 0 is a reading and not a blind spot. Function entries are unchanged: the V-NOC and postcss golden trees, wires and merged wires are byte-identical. A whole-project run (every def an entry, `measure_handed_over`) differs only in its `contexts` line, by exactly the number of classes (1084 -> 1079, 264 -> 245, 60 -> 58): a class is a `Construct` root now, not a context.

**Known gap, not fixed here** (closed by M step 4): a class declared **inside a function or a namespace** has its definition-time sites in no tree and no counter. The def around it stops at it (`Collector::collect` reads only its computed names), and `definition_sites` is for a class at the top of a file. Its decorators have `uncovered_local_class_decorator_sites`; its static initializers, static blocks and `extends` have nothing (test `class_entry_a_class_declared_in_a_function_...`, `newLocal`).

## TS5 step 5: cancel at every check, and the steps that cannot be stopped

`Cancel::after_checks(n)` (core, `a1ffe8f`) fires on its n-th check; `tests/cancel.rs` uses it to cancel a request at **every** check it makes, each on a fresh `Session`. A check is one `reason()` call: the solver's, before each context it would walk (after the budget), and `walk::body`'s, before each site. The engine is never asked.

**N, the checks of a request** (93 cases: the 6 scenarios, 76 entries of the policy table, the 11 `recursion` entries; dev profile, 8 s release / 11–12 s dev for 560 requests): scenarios N = 4 to 12, policy rows 0 to 46, `recursion` 2 to 29; 467 checks in all. N = 0 only for a class entry with no constructor: no context, so no check (below). **110 of the 467 cuts landed inside a body** (an `Incomplete` context with at least one edge). At every one of the 467: the graph passes `check_invariants`; each context is `Finished`, `Frontier` or `Incomplete(Cancelled)`; `Stats.cuts` is exactly `{Cancelled: the number of Incomplete contexts}`; a `Finished` context has the full graph's edges; an `Incomplete` one has the first sites' non-passed edges and no passed one, ending between two sites; the tree marks every cut context's expanded node `Incomplete`, and the wire (merged and not) carries `incomplete`; and the next request on the same session, with no cancel, is `==` the full graph (and its tree). With a budget (`max_depth` 1) the same holds, and below the root every context is a `Frontier` (`Cut`, never `Incomplete`).

**A `Recursive` leaf of a cut context is not marked `Incomplete`.** The renderer draws a leaf for a def already on the path, with `Recursive` and nothing about the def's status; the expanded node above it carries `Incomplete`. The test finds this at `scenario recursion-direct` and checks every cut context has an *expanded* node marked, and no expanded node is marked wrongly. Not a bug (the leaf says "see above"), but "every node that draws an `Incomplete` context" in the plan means the expanded ones.

**V-NOC `TaskDetailPanel`** (cold, release, `a_real_entry_…`, `#[ignore]`): N = 554 checks for 90 contexts. A cancel at check 1, 2, 3, 69, 138, 277, 415, 553, 554 gives 1, 1, 1, 20, 41, 56, 76, 90, 90 contexts, and each next request on the same session is the golden tree. The cancelled request at check 2 took **11 ms** and at check 1 0.8 ms: check 2 is the first site check of the root, after its sites were listed (below).

**A class entry with no constructor** is identical, graph and counters, under any cancel: `walk::construction` notes the counters before the solver runs, and with no `init` the solver has no context, so it makes no check (cancelled at 1, 2, 3 and already cancelled: equal to the uncancelled graph). A class with a constructor (`Rich`) is cut at its constructor and has the same `Stats.language` as the uncancelled request.

**[measure] the steps that cannot be stopped** (`measure_uninterruptible_steps`, `#[ignore]`, release, cold: a project opened afresh, every def asked once; two runs each, machine load 5 to 6, so read them to a factor of 2). Listing a body's sites (`Sem::call_sites`) happens before the first site check; resolving one site happens between two checks.

| | V-NOC frontend (1084 defs, 5765 sites) | postcss (a) (264 defs, 868 sites) | postcss (b) (60 defs, 293 sites) |
|---|---|---|---|
| listing a body's sites: **max** | **12.3–13.4 ms**, `CodeLinePopoverLayer` (18 sites) | 0.78–0.82 ms, `PreviousMap.consumer` (1 site) | 0.41–0.43 ms, `MapGenerator.constructor` (3 sites) |
| listing: median | 3.2–3.4 µs | 5.1–5.5 µs | 5.5–5.7 µs |
| resolving one site: **max** (after the listing, one process) | **9.6–9.8 ms**, site 92 of `CanvasView` (95 sites) | 79–92 µs, `LazyResult.catch` / `terminalHighlight` | 0.63 ms, site 2 of `MapGenerator.toBase64` |
| resolving one site: median | 1.75 µs | 1.5 µs | 1.6 µs |
| the max-listing def: its slowest site after the listing | 3.7–4.4 µs | 1 µs | 5.4–5.9 µs |
| the same def, on a project where nothing else was asked: its slowest site | 0.97–1.7 ms | 3.3–3.6 µs | 19–20 µs |

The maximum listing is **not** the first def of its file (the first-of-file maximum is 3 ms, V-NOC), so the 12 ms is not the file's outline. It is most likely the checker's first questions for that body (the property-access query asks the checker for a symbol once per body with a candidate); not isolated. So the listing and the site resolution both hold the engine's lazy work, which lands on whichever def asks first: about **13 ms** for the largest project here, a thousand times the median. A cancel waits at most that long on V-NOC (about 1 ms on postcss) before the next check.

**What §4 got wrong.** (1) "about one site's work": the largest uninterruptible step is the *listing* of a body, and it is not one site's work; on V-NOC it is 12–13 ms, with one site's resolution at most 9.6–9.8 ms. "Well under a millisecond on average cold" (S-TS3) is the average, not the bound; the bound is these two numbers. (2) The solver's check is after the budget (a context past the budget is `Frontier` even after a cancel), and again after a cut walk, to name the reason; neither shows in §4's table. (3) A body cut at a site keeps the sites before it and **not its hand-overs and counters**: they are noted after the loop. A cancelled request's `Stats.language` can therefore be below the uncancelled one's for a cut body (the next request is whole).

## TS5 row 3c: a coverage test for rule 8

`src/sem/coverage.rs` (`#[cfg(test)]`, inside `sem`: rule 4, no new public API; `calls::start_of` went from private to `pub(crate)`). **Every call-like node of a project's source is drawn in some tree, counted in some counter, left out by a stated policy, or a miss in a category on a list the owner decides.** Four tests: `each_coverage_fixture_has_its_nodes_accounted_for`, `every_miss_in_every_fixture_and_scenario_is_in_a_listed_category`, `the_list_has_no_stale_entry`, `the_counters_say_what_the_spans_say`; and the `#[ignore]` measure `measure_coverage`. The four count-only counters return their spans first (`0334771`, values unchanged, golden byte-identical).

**The scan** walks every node of every project file (and every repo `.d.ts`, whole-file ambient) with `for_each_child`. It reads the grammar for what is call-like: `CallExpression` (`super(…)`, `a?.b()` and `import(…)` included) and `NewExpression` anchor on the callee/class expression, `TaggedTemplateExpression` on the tag, `JsxOpeningElement` / `JsxSelfClosingElement` on the tag name, `Decorator` on its expression. It calls nothing of the walker (`Collector`, `body_of`, `def_of`, `is_plain_call`, `is_callee_position`, `call_sites`); it shares the span measure (`own_span`), the engine's `NodeFlags::Ambient` and `is_string_literal_like`. Excluded by policy, three entries: `import(…)` / `require("literal")` (a module load), an intrinsic JSX tag (`<div>`, `<my-el>`, `<svg:rect>`), ambient code. A miss gets its category from the parents (`category_of`).

**What is compared:** the graph of every def of the project as an entry (a class as its construction, `start_of`), one solver with `Limits::new(u32::MAX, None)` and the assertion that nothing was cut; an edge is at its context's def `range.start` + `site.start`. Counted: the four counters' spans for what the walker notes (`initializer_sites` over the `init_chain`, `definition_sites` and `computed_name_sites` of the class, `decorator_sites` of each class a non-class def's body declares), by file and span. One way: scanned ⊆ drawn ∪ counted. **The anchors line up exactly**, trivia included: on every fixture and every real project no miss has a drawn or counted span that starts where it does (`start_only` 0), and no two scanned nodes share an anchor (0). Every edge kind is relative to its def's start, passed edges too (`walk.rs`).

## TS5 step H: the hardening batch (H1–H10, 2026-11-17)

One commit each (`506f945` .. `dc1bc9a`, `10-review-fixes.md` §6). None changes an edge; H10 changes a reason.

- **H1, one checker handle at a time.** `Sem::checker()` is the only place that calls `get_type_checker`, and it returns a guard
  (`HeldChecker`, `Deref` to the `Checker`). The guard sets `Sem::checker_held` and clears it on drop. A second handle while one is held is a
  `debug_assert!` with a message, where it used to wait for ever: the checker is behind a mutex that one thread cannot lock twice. A
  `#[should_panic]` test takes two (debug builds only), and its twin takes one, drops it and takes another.
- **H2.** The two memory tests share one `static Mutex<()>`, so they take turns (the file went from about 7 s to 9.6 s).
- **H3.** `handed_not_called` sorts with `found.sort()`, by `StableDef`'s own order, not by its `Debug` string.
- **H4.** `Sem::_region` is `region` (it is used). The header of `tests/threads.rs` said `Sync`; it says `Send` and not `Sync`, as pinned since TS4
  ("Thread safety of the handles").
- **H5.** `matches_a_glob` reads `ENVIRONMENT_GLOBS` instead of repeating its names; a unit test checks that each glob matches a name written from it.
- **H6.** A request with `occurrence` above 0: `Box.value` occurrence 0 is the getter, 1 the setter, 2 is no def (D15).
- **H8.** `under_root` takes the root's trailing `/` off first, so a drive root (`C:/`, `/`) has files under it; a path equal to the root is `None`.
- **H10.** The call of a function expression written in place (`(() => {})()`, `(function () {})()`, `(async () => {})()`, `!function () {}()`, under
  parentheses and assertions) is `Unresolved(anonymous_function_called)`, not `no_declaration`: the same edges, a truer reason. No snapshot
  held such an edge. postcss (a) `Processor.process` keeps its one `no_declaration`, which is not an IIFE. **Found, H11:** a *named* function
  expression called in place gets the same reason, and its calls are in no tree but its own (`10-review-fixes.md` §6, H11).
- **H11 (D40, `6c1dfc4`).** Where the callee is resolved, `function_called_in_place` (one helper for H10 and H11) looks under parentheses and
  the assertions (`<T>`, `as`, `satisfies`, a postfix `!`) for an arrow or a function expression. A **named** function expression that
  `def_of` holds is resolved to that def before the engine is asked, through `classify`, as any declaration is: a `Call`, drawn with its body
  (`named ▸ h`). An anonymous one stays `anonymous_function_called`. It does not look through a prefix inside the parentheses

## TS5 step 6 design: what the engine gives for following the disk (2026-11-17)

**[ran]** with a throwaway probe in a scratch worktree (deleted), on the pin `13a31a4`. The design is
`docs/03-typescript/11-step6-text-and-disk.md`.

- **The program keeps no failed lookups.** `Program::missing_files` holds root and referenced files it could not open, behind a "testing
  only" accessor (`tsrs_compiler/src/program.rs:3134`); `get_unresolved_imports` gives module specifiers, not paths.
- **The file system wrapper does.** `tsrs_vfs::trackingvfs::FS` records the path of every `file_exists`, `read_file`, `directory_exists`,
  `get_accessible_entries`, `stat` and `realpath`, missing paths included. The engine's watch mode builds each program on a fresh `cachedvfs`
  inside a `trackingvfs` and watches the seen paths (`tsrs_execute/src/watcher.rs:778`).
- **On V-NOC** (`TaskDetailPanel`'s program, dev profile): 9143 paths seen after open (2616 files, 852 directories, 5675 missing), the same
  9143 after a body is walked; 8057 under `node_modules`. A `stat` of all of them takes 14 to 18 ms, and of the 1086 outside `node_modules`
  1.5 ms. `Sem::open` took 241 ms.
- The config host reads through the same file system, so the `include` folders are tracked; the bundled libraries are not (`bundled::wrap_fs`
  is outside the tracker).
- **No overlay fits:** `wrapvfs::wrap` takes a `&'static dyn FS`, and `tsrs_project`'s `snapshotfs` belongs to the language server. An
  overlay would be a small `FS` of our own in `sem`. It is **not built**: only saved text is read, for now (D42; the design is kept in
  `11-step6-text-and-disk.md` §10).
- **Checked at the design's review (2026-11-17):** module resolution asks `directory_exists` of each `node_modules` folder before it looks
  inside (`tsrs_module/src/resolver.rs:1744`), so the folders themselves are among the seen paths and can be stamped. The nearest config with
  a syntax error is `OpenError::ConfigError` (`sem/project.rs`), so a config saved half-edited fails a rebuild: the reason a lost session
  must come back by itself (the design's §3).


## TS5 step 6, commit 1 as built: the tracker and the stamps (`d3b394e`, reviewed 2026-11-19)

- **The tracker's handle.** `sem::tracked_fs()` makes `Arc<trackingvfs::FS<cachedvfs::FS<&'static dyn FS>>>` and puts a clone of the `Arc`
  inside `bundled::wrap_fs(…)`: an `Arc<T>` of a file system is itself a file system (`FS` is implemented for it), so the clone goes into
  the stack and the original stays in `Sem::open_tracked`. `seen_files()` is read after the build returns, so it is there when the build
  fails. The cache is made for each build.
- **What a small project asks for** (two source files, one failed import, a `tsconfig.json`, no `node_modules`; the list was printed
  once by the reviewer): 29 paths. 3 files (the config and the two sources); 10 directories: the root, `src`, and **the 8 directories

  import (`gone`, `.ts`, `.tsx`, `.d.ts`, `.js`, `.jsx`).
- **No `node_modules` path is asked for** in that project: nothing imports a package, and no `node_modules/@types` folder is looked for
  either. With an import of a package, the `node_modules` folder is among the seen paths (cases 8 and 14 rest on it).
- **A walk adds no path:** the seen paths after a call graph are the seen paths after open (`sem/tests.rs`, kept as a test).
- **Spelling:** the engine's paths are absolute, with `/`, and canonical (`/private/var/…` on macOS), and `std::fs::metadata` takes them
  as they are.
- **A file rewritten in place inside a package does not move the folder's modified time**, so a stamp on `node_modules` and its lock
  files cannot see a package edited by hand (case 8; `reload` does).
- **The directories above the root must not be stamped** (found at the review; the design's §5, step 1b). The home folder's modified time
